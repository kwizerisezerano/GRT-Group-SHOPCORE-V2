# ShopCore V2 — Codebase Audit vs. Requirements Notes

**Date:** 2026-08-04
**Scope:** Verification of the existing repository against `# SHOPCORE REQUIREMENTS NOTES.md`
**Branch:** `claude/shopcore-review-setup-52k1qe`

---

## 1. Summary

The repository is a **working React/Vite ERP application** (135k LOC) sitting on top of Supabase,
with a **new Node/Express + Prisma + MySQL backend** (1.5k LOC) that has begun replacing Supabase
module by module. Roughly **10% of the backend migration is done** — auth and workspace bootstrap
only.

The backend's chosen stack matches the requirements. **The frontend's does not.** The requirements
specify Nuxt + Vuetify + Montserrat; the codebase is React + Tailwind/shadcn + Inter. This is not a
gap that can be closed incrementally — it is a decision that must be made before further work.

| Area | Verdict |
|---|---|
| Project structure (backend/frontend split) | Mostly compliant |
| Backend framework (Node.js) | Compliant |
| Database (MySQL) | Compliant, but two competing schemas |
| Backend feature coverage | ~10% built |
| Sensitive-data encryption | Not implemented as specified |
| Frontend framework | **Non-compliant — different stack entirely** |
| Backend as sole data source | **Non-compliant — 68 files bypass it** |

`frontend/src/`.

## 3. Backend Verification

### 3.1 What is actually wired

`src/app.ts` mounts exactly two routers:

| Router | Endpoints |
|---|---|
| `/api/auth` | signup, login, refresh, logout, me, is-platform-admin, password-reset/request, password-reset/complete |
| `/api/workspace` | plans, payment-methods, pending |

Plus `/api/health`, `/api/openapi.json`, `/api/docs`, `/api/realtime/:channel`, `/uploads`.

**~11 business endpoints total.** No products, sales, POS, inventory, customers, suppliers,
purchases, expenses, staff, or platform-admin routes exist.

### 3.2 Dead scaffolding

These files are written and typecheck cleanly but are **referenced by no module**:

- `src/lib/crudModuleFactory.ts` — generic tenant-scoped CRUD router builder
- `src/lib/stockMovement.ts`
- `src/lib/storage.ts` — local-disk / S3 driver
- `src/lib/realtime.ts` — mounted in app.ts, but nothing publishes to it

They are ready to use; they represent the intended shape of the next phase.

### 3.3 Strengths worth keeping

- **`src/lib/tenantScope.ts`** — a Prisma `$extends` client that auto-injects `tenantId` on every
  read/write for 24 tenant-scoped models. This is a genuinely good replacement for the Postgres RLS
  that MySQL lacks.
- **`src/middleware/errorHandler.ts`** — consistent `{ error: { code, message } }` shape, correct
  handling of `ZodError` → 400.
- **`src/config/env.ts`** — Zod-validated env with fail-fast on boot.
- Refresh-token rotation with revocation, and password reset that revokes all sessions.
- Password reset does not leak account existence (always returns 202).

### 3.4 Two competing database schemas

| Source | Content |
|---|---|
| `backend/prisma/schema.prisma` | 35 models, one Prisma migration, drives the running app |
| `database/mysql_schema.sql` | 33 hand-written tables, separate runner script, drives nothing |

They overlap heavily but are not generated from each other. `mysql_schema.sql` has tables Prisma
does not model (`stock_movements`, `audit_log`, `system_performance_logs`, `backup_history`,
`workspaces`). **This will drift.** One must become the single source of truth.

## 4. Requirement-by-Requirement: Backend

### 4.1 Sensitive Data Security — **NOT MET**

Required: AES-256-GCM for names/emails/phones; HMAC-SHA256 for email and phone.

Actual:

- Encryption happens **in the browser**, in `frontend/src/lib/encryption.ts`, using
  `CryptoJS.AES.encrypt`. That default is **AES-256-CBC** with OpenSSL `EVP_BytesToKey` key
  derivation — **not GCM**, and with **no authentication tag**, so ciphertext is malleable and
  tampering is undetectable.
- The key comes from `VITE_ENCRYPTION_KEY`, a Vite client variable. **It is compiled into the
  JavaScript bundle and is readable by anyone who opens the app.** It also falls back to the
  literal string `'shopcore-default-key-change-in-production'` when unset.
- The backend treats `displayName` and `phone` as opaque ciphertext (`VarChar(512)`) and never
  encrypts or decrypts anything itself.
- **Email is stored in plaintext** in `users.email` with a unique index — it is the login
  identifier.
- `grep -i hmac` finds HMAC-SHA256 used **only** for hashing refresh/reset tokens
  (`src/lib/jwt.ts`). There is no `email_hash` or `phone_hash` column anywhere in either schema.
- `grep -i gcm` returns nothing across the entire codebase.

This requirement needs to be built from scratch, server-side.

### 4.2 Database (MySQL) — **MET, with caveats**

MySQL 8 + Prisma, real foreign keys, `onDelete: Cascade` where appropriate, unique constraints on
`users.email`. Tenant isolation enforced in application code via `tenantScope.ts` since MySQL has
no RLS. Caveat: the dual-schema problem in §3.4, and `TENANT_SCOPED_MODELS` is a hand-maintained
list — a model added to `schema.prisma` without a matching entry there will **silently query
across all tenants**. That is a latent data-leak footgun.

### 4.3 Email Notification — **PARTIAL**

Only one email exists: password reset, via Resend, translated into en/fr/rw/sw. No account
notifications, system alerts, user-action or transaction emails. No template system, no queue, no
retry. Without `RESEND_API_KEY` the reset link is logged to the server console.

### 4.4 Fields Validation — **MET for what exists**

Zod schemas on all auth routes; `ZodError` → 400 with flattened field details. Password minimum is
8 characters with no complexity or breach checks.

### 4.5 Backend Technology (Node.js) — **MET**

Node ≥20, Express 4, TypeScript 5.5, CommonJS. `npm run typecheck` passes clean.

### 4.6 Multi-language Support — **MISMATCH**

| Required | Implemented |
|---|---|
| English (en) | Yes |
| Swahili (sw) | Yes |
| **Spanish (es)** | **Missing** |
| French (fr) | Yes |
| — | Kinyarwanda (rw) — present, not in requirements |

Both `backend/src/lib/email.ts` and `frontend/src/i18n/` implement en/fr/rw/sw. The
`Profile.language` column and the signup Zod enum are both hardcoded to `["en","fr","rw","sw"]`.
Adding `es` touches the enum, the DB column comment, the email copy table, and four locale
directories. Whether `rw` should be dropped is a product decision — the README advertises it.

### 4.7 File and Image Storage (Cloudinary) — **NOT MET**

`src/lib/storage.ts` implements a local-disk driver and an S3-compatible driver. There is **no
Cloudinary SDK, no Cloudinary config, no Cloudinary upload path**. The only occurrence of the word
in the repo is a hardcoded logo URL inside a legacy Supabase edge function.

### 4.8 API Response Standards — **PARTIAL**

Correct codes are used: 200, 201, 202, 204, 400, 401, 403, 404, 409, 500. Errors are consistently
`{ error: { code, message } }`. **Success responses are not consistent**: some return `{ data }`,
some return `{ plans }`, some return a bare object, some return a `message`. The requirement that
*every* response carry a clear explanatory message is not satisfied — most success responses have
no message field at all, and no response is localized.

### 4.9 Swagger Documentation — **PARTIAL**

Swagger UI is served at `/api/docs` from a hand-written spec in `src/docs/openapi.ts` (252 lines).
It covers the 11 endpoints that exist. It is maintained by hand and will drift from the Zod
schemas; generating it from Zod (e.g. `zod-to-openapi`) would keep them in sync.

### 4.10 API Testing — **NOT MET**

The backend has **zero tests** and no test runner in `package.json`. (The requirement names
"AppIDong" — presumably **Apidog**; no collection exists in the repo either way.) The frontend has
Vitest configured with 2 test files and a Playwright config.

## 5. Requirement-by-Requirement: Frontend

### 5.1 Framework — **NOT MET**

| Required | Actual |
|---|---|
| Nuxt (Vue) | **React 18 + Vite 5 + React Router 6** |

`grep -i "nuxt\|vue"` across all package manifests returns **nothing**. There is no Vue code in the
repository. 139 pages and 111 components are React `.tsx`.

### 5.2 Design and UI — **NOT MET**

| Required | Actual |
|---|---|
| Vuetify | **Tailwind 3 + shadcn/ui + 49 Radix primitives** |
| Montserrat | **Inter** (`tailwind.config.ts:27`, `index.css:1` Google Fonts import) |
| Professional, responsive | Met — the existing UI is genuinely polished and responsive |

The font is a one-line change. Vuetify is not — shadcn/ui and Vuetify are incompatible component
models, and every one of the 111 components is built on Radix primitives.

### 5.3 Direct Field Validation — **MET**

`react-hook-form` + `@hookform/resolvers` + `zod` are in place.

### 5.4 Backend Message Display — **PARTIAL**

`ApiError` carries `status`/`code`/`message` and surfaces backend text via `sonner` toasts — but
only on the **7 files** that use `apiClient`. The other 68 surface Supabase's messages instead.

### 5.5 Backend as the Main Data Source — **NOT MET**

This is the largest frontend gap.

- **68 files import the Supabase client directly** (38 `supabase.` call sites). The required flow
  is `Frontend → API → Backend → Database`; the actual flow for most of the app is
  `Frontend → Supabase → Postgres`.
- Four Supabase **edge functions** are still invoked at runtime: `ebm-vsdc` (from `POS.tsx`,
  `Sales.tsx`, `EBMSettings.tsx`) and `ai-assistant` (from `AIAssistant.tsx`).
- **Hardcoded business data ships in the frontend.** `src/data/mockProducts.ts`, `mockSales.ts`,
  `mockCustomers.ts`, `mockExpenses.ts` are imported not just by landing-page components but by
  **real application pages**: `pages/Products.tsx`, `pages/Customers.tsx`, `pages/Expenses.tsx`.

## 7. The Decision That Blocks Everything Else

Backend requirements can all be met incrementally on the existing foundation — the architecture is
sound and the remaining work is additive.

The frontend cannot. Requirements F1 and F2 describe a **different application** from the one in
this repository. Three paths:

**A — Rewrite the frontend in Nuxt + Vuetify.** Full requirement compliance. Cost: re-implementing
135k LOC across 139 pages and 111 components. The React app's offline engine, Tauri desktop shell,
i18n system, and landing experience would all need porting. This is measured in months.

**B — Keep React, revise the requirements.** Adopt Montserrat (trivial), finish the Supabase →
backend migration, and deliver every backend requirement. Requires sign-off from whoever authored
the notes that Nuxt/Vuetify were a preference rather than a constraint.

**C — Hybrid.** Freeze the React app, build new modules in Nuxt behind a shared backend. In
practice this means maintaining two frontends and is rarely worth it.

**Recommendation: B**, unless the Nuxt/Vuetify requirement is contractual. The backend is where the
real requirement gaps are (encryption, Cloudinary, Spanish, emails, tests, ~90% of endpoints), and
that work is identical under any of the three paths.

## 8. Suggested Sequence (backend-first, path-independent)

1. **Single source of truth for the schema** — retire `database/mysql_schema.sql` or regenerate it
   from Prisma; fold in the tables Prisma is missing.
2. **Server-side crypto module** — AES-256-GCM encrypt/decrypt with a server-held key, plus
   `email_hash` / `phone_hash` HMAC-SHA256 columns with unique indexes for dedup and lookup.
   Retire `VITE_ENCRYPTION_KEY` and migrate existing ciphertext.
3. **Response envelope** — one shape for success and error, always carrying a localized `message`.
4. **Cloudinary storage driver** alongside the existing local/S3 drivers.
5. **Spanish locale** across the enum, email copy, and locale files; decide `rw`'s fate.
6. **Build out the modules** using `crudModuleFactory` — products, categories, brands, suppliers,
   customers, sales, purchases, expenses, staff — cutting the frontend over file by file and
   deleting the corresponding Supabase calls and mock imports as each lands.
7. **Notification service** for account/transaction/alert emails.
8. **Tests + Apidog collection** as each module lands, not after.
9. **Generate Swagger from Zod** so docs cannot drift.

Also worth fixing early: make `TENANT_SCOPED_MODELS` fail closed (assert every model with a
`tenantId` field is listed) so a forgotten entry cannot silently leak across tenants.
